# Codex 全局开发指令 v2.4

> 部署：复制到项目根目录 `AGENTS.md`（或 `~/.codex/AGENTS.md`，二选一）。
> 流程全文见 zwmhua/Solo-Flow 的 `WORKFLOW.md`；本文件只管 Codex 怎么执行。

## 1. 原则
- 默认简体中文；代码、命令、路径保持原样。
- 正确优先于速度，证据优先于声明，最小修改优先于重构，安全优先于自动化。
- 没实际运行过的东西，不写"通过"。

## 2. 授权范围
- Human 派发一个 Issue（或快车道指令），就授权了以下动作：在白名单内开发、跑定向测试、本地提交、推送 `task/N` 分支、提 PR。
- 你的任务到"提出 PR"为止。
- 以下动作必须 Human 对具体动作明确授权：合并、部署、rebase / 强推 / 改写历史 / revert、不可恢复删除、生产数据、凭据或权限变更、明显付费或大规模的调用。
- **永远不能改**：`.github/workflows/`、`STATUS.md`、`docs/nodes/`、红牌文件（见 `ARCHITECTURE.md`），除非 Issue 逐个文件明确授权。

## 3. 开工前核对（不符就停下报告 = X1）
1. 读 `ARCHITECTURE.md` 和指定的 Issue；读不到就停，不凭记忆去猜。
2. `git status`：有未提交或未知的改动，就停下，保留现场，不清理也不覆盖。
3. 核对仓库、分支、HEAD 和 Issue 写的基线是否一致；基于最新 main 建 `task/N` 分支。已有同名分支或 PR 时，先核对状态，不覆盖。
4. 白名单以 Issue 为准，快车道以 Human 指令里写的为准。
5. `AGENTS.md`、`ARCHITECTURE.md`、Issue 三者互相冲突，或者和现有代码对不上时，停下报告，不自己挑一个。

## 4. 实施
1. 先把 Issue 的验收点原样写成测试，再写业务代码。不删、不弱化断言，也不为了迁就实现去改测试。
2. 只改白名单内的文件；目录名、文件名、函数名要和 Issue 契约完全一致。
3. 测试只能依赖已提交到仓库的文件。
4. 默认不新增依赖。
5. 不吞异常，不伪造收据，不把失败当成功。拿不准安全时默认拒绝；Mock、Worktree 不等于安全沙箱。
6. 不覆盖受保护的 `out`、缓存和历史证据；秘密不进日志、提交或 PR。

## 5. 停下来问（= X2）
- 需要新依赖，或者需要白名单外的文件。
- 业务代码加测试的增删超过 **200 行**（不算锁文件、自动生成文件、STATUS 和 docs），无论是估算还是实际 diff 超出。
- 需要新增 Issue 里没有的行为规则。
- 测试意外调用了真实服务，或者出现越权、数据损坏风险：立即停手，保留现场和日志。

## 6. 提 PR
按项目里的 PR 模板填写：
- `closes #N`；快车道写"快车道：<一句说明>"
- 改动文件
- 测试命令
- 未验证项

测试结果以 Actions 为准，不在 PR 里写"已通过"之类的自述。

## 7. 打回修复
- 修之前先补一个会失败的测试，再修；不改已有测试。
- 只修已证实的问题，修完在 PR 下说明改了哪些文件。
- 同一张卡这是第 3 次回修时，先停下，报告"建议回大脑重新三问"，不再动手。

## 8. 每次停下都留痕
X1、X2、BLOCKED、回修，各在 Issue 或 PR 评论里留一行：时间、原因、当前状态。
